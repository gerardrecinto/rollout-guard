rollout-guard watches a deployment's health window right after a release. Known failure signatures get a rollback, restart or scale. Unknown ones are escalated, never guessed at. Every decision lands in a JSONL audit trail.

How it works

About 380 lines of standard-library Python. You can read all of it in one sitting.

1

Build a window

Metric samples and log lines from the minutes after a deploy. Restart counters are compared as a delta across the window, so old restarts do not trigger a false rollback.

2

Match signatures

Each rule is a metric threshold or a log pattern mapped to one action. The verdict is healthy, degraded or failing.

3

Plan one action per type

Two rules that both want a rollback produce one rollback. Worst severity goes first. Every decision, including dry runs, is appended to the audit trail.

Safety model

The point is that it is boring to trust. These are properties of the code, not intentions.

PropertyWhat it means
Dry-run default--execute is an explicit opt-in per invocation.
Closed action setrollback, restart, scale or escalate. There is no path from a rule file or an LLM reply to an arbitrary shell command.
LLM suggests onlyThe fallback classification is validated against the same action set, audited, and never executed.
One action per typeDuplicate demands collapse, so a bad window cannot fire ten rollbacks.
Everything auditedDry runs and escalations are written as replayable JSONL.

Design reasoning is in ADR 001.

Run it on your own cluster

Python 3.9 or later, standard library only.

pip install git+https://github.com/gerardrecinto/rollout-guard

rollout-guard validate --rules rules.json
rollout-guard check \
  --metrics metrics.json --rules rules.json \
  --deployment api --namespace prod
rollout-guard report
[
  {"name": "error-spike", "action": "rollback",
   "metric": "error_rate", "threshold": 0.05},
  {"name": "oom-kill", "action": "scale",
   "log_pattern": "OOMKilled", "scale_to": 4}
]

Add --execute to run the commands. Add --llm-fallback with ANTHROPIC_API_KEY set to classify degraded windows no rule explains.

What this does not do
  • It reads exported samples. It does not scrape Prometheus or CloudWatch for you.
  • It acts on thresholds you wrote. A threshold that is wrong for your service is wrong here too.
  • It does not coordinate with a progressive-delivery controller. Use it as a check on top, not instead of canary analysis.
